数据迁移路径 — 选一种

目标模型已定（方案 A）。现在决定怎么把现有字符串数据搬到 ID 引用。两者都包含同样的 7 个原子步骤，区别在「是否分阶段」。遵循 model/main.go 现有迁移模式（ADD COLUMN 等，兼容三种 DB）。

共同的 7 个原子步骤
  1. 建表：groups、channel_groups；给 users / abilities / token 加 group_id 列
  2. 扫描唯一分组名：汇总自 users.group、channels.group(拆逗号)、token.group、abilities.group
  3. upsert groups：为每个唯一名建实体（ratio 取自 GroupRatio map，default 作为系统保留分组）
  4. 回填 group_id：users / abilities 按 name→id 回填；token 空串→0（跟随用户）
  5. 建 channel_groups：拆 channels.group 逗号串 → (channel_id, group_id)
  6. 切换读路径：代码读 group_id 而非 group 字符串
  7. 清理：删除旧 group 字符串列、channels.group
1

一次性迁移（维护窗口）

7 步在一个迁移事务 / 短暂维护窗口内全部完成，切换后立即删除旧列。

优点

  • 代码简单，无过渡态
  • 迁移完即彻底干净

缺点

  • 需要停机/维护窗口（大表回填耗时长）
  • 出错回滚成本高
2

双轨过渡（在线分阶段）⭐ 推荐

分 4 个 phase 在线推进，每阶段可独立验证、可回滚，全程不停服。

P1 加列+建表+回填（在线，旧路径照跑）
↓ P2 双写（写时同时维护 group_id 和旧 group 名）
↓ P3 切读（读优先 group_id，可灰度）
↓ P4 下线旧 group 列、channels.group

优点

  • 无需停机，可灰度、可回滚
  • 生产系统最安全

缺点

  • 双写逻辑复杂、过渡期长
  • P2–P3 期间改名仍需同步旧名列

我推荐双轨过渡（生产安全、可灰度）。若你能接受短暂维护窗口、且数据量不大，一次性更省事。怎么选？
