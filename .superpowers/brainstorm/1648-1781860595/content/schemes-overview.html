分组关联重设计 — 选一个目标模型

三者都引入 groups 实体表、用 ID 引用解决「改名级联」。差异在「渠道多分组怎么存」和「迁移激进度」。历史表(logs/tasks/subscription/perf_metric)三者都不动，保留旧名快照。

三者共用的 groups 实体表
groups（新增表）
id · name(unique) · description · status(enabled/disabled) · group_ratio · topup_ratio · sort · created_at · deleted_at(软删除)

改名 = 改 name 一行；删除 = 软删除(status=disabled)，引用保留不丢。

A

规范关系模型（关联表）⭐ 推荐

渠道多分组用独立 channel_groups(channel_id, group_id) 多对多关联表；users / abilities / token 全部用 group_id 外键引用。

users.group_id  → groups.id
channel_groups(channel_id, group_id)  ← 多对多
abilities 主键: group_id + model + channel_id
token.group_id

优点

  • 最规范，改名彻底零级联
  • 查询/索引清晰，跨 DB 友好
  • 最符合「一等实体 + 彻底治理」

缺点

  • 改动最大：新增关联表、abilities 复合主键变更、前端下拉改造
  • 渠道选择/缓存逻辑要适配关联表
B

ID 化 + 渠道 JSON 字段（折中）

users / abilities / token 用 group_id；渠道多分组用 channels.group_ids（TEXT 存 JSON/逗号 ID 串），不建关联表。

users.group_id  → groups.id
channels.group_ids (TEXT: [1,2,3])
abilities 主键: group_id + model + channel_id
token.group_id

优点

  • 不新增关联表，channels 结构改动最小
  • 改名仍零级联（存的是 ID）

缺点

  • JSON 数组跨 DB 查询/索引弱（Rule 2 需用 TEXT）
  • 范式不如关联表，按分组反查渠道要解析
C

双轨过渡（ID + 名称快照，渐进迁移）

目标模型同 A（或 B），但 A 类表同时保留原 group(字符串)列做显示快照，双写过渡；全部回填后下线字符串列。

users: group_id + group(名·过渡)
abilities: group_id + group(名·过渡)
…双写期… → 回填完成 → 删除名列

优点

  • 可灰度、可回滚，生产迁移风险最低
  • 过渡期前端/API 可逐步切

缺点

  • 双写逻辑复杂、过渡期长
  • 过渡期改名仍需同步名列（未彻底）
我的推荐

方案 A 的目标模型 ＋ 方案 C 的渐进迁移路径：目标一步到位用规范关联表（彻底解决改名），但迁移走双轨回填保证生产安全。也可单选某一个——比如只想最小改动就选 B。
